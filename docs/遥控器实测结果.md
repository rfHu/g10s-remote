# 你这支遥控器的实测身份（2026-11-17 查询）

## 一、能确认的硬件信息

| 项目 | 值 | 来源 |
|---|---|---|
| 系统内设备名 | `Google TV Remote` | PnP FriendlyName |
| 蓝牙地址 | `C4:19:D1:9B:34:D1` | DEVPKEY_Bluetooth_DeviceAddress |
| 设备类别 | `Input.Remote` | DEVPKEY_DeviceContainer_Category |
| **Model Number（DIS）** | **`ZTKA-IR57`** | DIS 型号字符串，Windows 已缓存 |
| **VID / PID** | **`0x18D1` / `0x9451`** | DIS PnP ID 特征 |
| PnP 产品版本 | `0x0105`（即 1.0.5） | DEVPKEY_Bluetooth_DeviceProductVersion |
| **芯片厂商 ID** | **`1602` = `0x0642` = Bluetrum Technology（中科蓝讯）** | ManufacturerId |
| LMP 版本 | `13`（0x0D，按规范对应 Core 5.4） | LmpVersion |
| 序列号样字符串 | `57211NXAO100CI` | 未命名的 PnP 属性 |

**固件版本字符串（Firmware Revision，DIS 特征 `0x2A26`）没有出现在 Windows 的缓存里**，需要主动连 GATT 去读，见第三节。

## 二、最重要的两条结论

### 1. 这不是原装 G9N9N，是第三方兼容款

- 文档里的原装 Chromecast 遥控器是 **PID `0x9450`**，而这支是 **`0x9451`**
- 型号字符串 `ZTKA-IR57` —— 典型的国内 ODM 命名（`IR` 说明带红外，用于控电视音量/电源）
- 蓝牙芯片厂商 ID 指向**中科蓝讯（Bluetrum）**，不是 Google 自己的方案
- 它只是**冒用了 Google 的 VID（0x18D1）+ 仿了一个接近的 PID**，好让主机把它当成 Google 遥控器

这正好解释了两件事：

1. 为什么 MoteDeck 的 README 特意写"谷歌 TV 遥控器均为第三方生产，存在多个版本，不能保证所有版本都可以使用"
2. 为什么网上"15 元 G9N9N"的坑那么多 —— 商品页写 G9N9N，实际芯片、固件、按键报文都可能不一样

**影响**：协议层可能对得上，也可能对不上，只能实测。但下面这条是好消息。

### 2. 好消息：ATVV 语音服务在

Windows 已经把它的 GATT 服务表全枚举出来了（`DEVPKEY_Device_Siblings`），其中：

```
00001800  Generic Access
00001801  Generic Attribute
00001812  HID over GATT（HOGP）      ← 按键走标准 HID
0000180f  Battery Service            ← 有电量上报
00010203-0405-0607-0809-0a0b0c0d1912 ← 语音遥控器协议常见的服务 UUID
ab5e0001-5a21-4f05-bc7d-af01f617b664 ← ATVV 语音主服务，确认存在 ✅
d343bfc0-5a21-4f05-bc7d-af01f617b664 ← Google 私有服务（疑似遥控器管理/配对）
18030001-5a21-4f05-bc7d-af01f617b664 ← Google 私有服务（疑似 OTA）
0000ff12-...                          ← 厂商自定义
```

`AB5E0001` 在，说明**这支遥控器大概率支持 ATVV 语音协议**，语音输入这条路是通的。剩下要验证的只是"它的 opcode 时序和原装是否一致"。

## 三、固件版本怎么拿到

Windows 只缓存了 DIS 的型号字符串，没有缓存固件修订号。三条路：

### 路线 1：跑脚本读 GATT（最准）

```bash
pip install bleak
python read_dis.py
```

`read_dis.py` 会连上去把 DIS 的全部字符串读出来：厂商名、型号、序列号、硬件版本、**固件版本**、软件版本、PnP ID，顺带把 ATVV 服务的特征列出来——这一步同时验证语音链路。

如果报连不上，先按一下遥控器任意键唤醒它（它会休眠），再跑一次。

### 路线 2：从电视端看

把遥控器配对回 Google TV，在 `设置 → 遥控器和配件 → 选中这支遥控器`，部分固件会显示版本号。缺点是要拆回电视，而且第三方兼容款不一定有这一项。

### 路线 3：看电池仓标签

第三方 ODM 的型号、批次、认证号通常印在电池盖内侧的标签上。`ZTKA-IR57` 这个字符串应该能在上面找到，同一行往往还有 FCC ID / 生产批次 —— 这是唯一"不依赖软件"的准确来源。

## 四、对下一步的影响

| 环节 | 判断 |
|---|---|
| 按键映射 | 服务里有 `0x1812` HOGP，说明按键走标准 HID，MoteDeck 应该能收 |
| 语音输入 | ATVV 服务在，有希望；但要实测 opcode 是否按 v1.0 走 |
| 固件升级 | 有 `18030001` 疑似 OTA 服务，但第三方固件基本不会有更新 |
| 兼容风险 | 型号非标，MoteDeck 的设备扫描可能识别不了 —— 那就得走自研 ATVV |

建议顺序：先跑 `read_dis.py` 拿到固件版本 + 确认 ATVV 特征齐不齐，再决定上 MoteDeck 还是自己写。固件版本对排查很关键——如果它报的 revision 和已知的 G9N9N 差很远，那基本可以判定协议实现是另一套。

## 五、MoteDeck 实际支持的 Google 遥控器范围（源码核对）

README 写得含糊（"Google TV 款的谷歌遥控器"），实际清单在仓库 `device-profiles/*.json`，全部就 4 个：

| profile id | 设备 | 定位 |
|---|---|---|
| `xiaomi-rc003` | 小米蓝牙遥控器 2 Pro | 主力适配 |
| `xiaomi-rc001` | 小米蓝牙遥控器 2 | 同按键布局 |
| `chromecast-remote` | 谷歌 Chromecast 遥控器 | 研究阶段 |
| `dji-mic-2` | DJI Mic 2 | 纯录音输入，不可映射 |

**Google 只有一条**，`chromecast-remote.json` 原文：

```json
"displayName": "谷歌 Chromecast 遥控器",
"model": "Chromecast Voice Remote",
"support": { "status": "research" },
"identity": {
  "bluetoothNames": ["Chromecast Remote"],
  "hid": { "vendorId": 6353, "productId": 37968 }
}
```

拆开看三个要点：

1. **状态是 `research`，不是 `implemented`**（可选值只有 implemented / research / planned / unsupported）。也就是说官方自己也没把它当"已支持"。
2. **只认一个型号**：`Chromecast Voice Remote`，即原装 G9N9N（VID `0x18D1` = 6353，PID `0x9450` = 37968）。Google TV Streamer 的 GY3LE、任何第三方兼容款都没有 profile。
3. **扫描时只用蓝牙名做精确匹配**（`identity.matches_chromecast_name`），白名单就是 `["Chromecast Remote"]` 这一个字符串。VID/PID 记在 profile 里，但扫描逻辑不读它。

另有两条硬性前置：设备必须**已配对**，且能读出合法 ContainerId（`{00000000-...}` 这类无效），否则直接跳过。profile 不在 `KNOWN_PROFILES` 里时，`add_device` 会抛"这台设备暂未适配，不能添加。"

### 对照你这支

| 判据 | MoteDeck 要求 | 你的设备 | 结果 |
|---|---|---|---|
| 蓝牙名 | `Chromecast Remote` | `Google TV Remote` | ✗ |
| PID | `0x9450` (37968) | `0x9451` (37969) | ✗ |
| 型号串 | — | `ZTKA-IR57` | 无对应 profile |

**两条都不满足，设备页会把它列为"不支持"，加不进去。**

注意 PID 只差 1（9450 → 9451），这不是巧合——兼容款在仿 Google 的 PID 时顺手加了个一，结果反而把"能不能被识别"这件事卡死了。

### 可以试的绕过

在 Windows 蓝牙设置里把这台设备**重命名**为 `Chromecast Remote`，看能不能过名称门槛。但要清楚代价：

- 只过了名称检查，ATVV 协议是否按 v1.0 走仍然未知，要实测
- Chromecast 的按键链路在 MoteDeck 里不走普通 Raw Input，JSON 里明确写"按键报告不在标准 HID 通道内，提权后由 HID 输入钩子接收"，需要管理员权限
- 官方状态本身就是 research，等于你在替作者做真机验证

### 其他两个项目的范围

| 项目 | Google 遥控器支持 | 依据 | 状态 |
|---|---|---|---|
| `zfdang/remote-buddy-windows` | G9N9N（`0x18D1:0x9450`，名 `Chromecast Remote`）；GY3LE 列为"计划支持" | 名称 + VID/PID | Windows 待真机验收 |
| `zolo1978/google-remote-voice-mac` | G9N9N 家族（`18D1:9450`，DIS A0，固件 26.7 实测） | VID/PID | macOS 0.1 实验版 |
