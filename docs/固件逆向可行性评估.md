# 固件逆向可行性评估（2026-11-20）

## 结论

**放弃固件逆向，维持现有的用户态「钩子拦截 + 注入」方案。** 三条独立依据，任何一条都足以否决：

1. **软件侧没有固件入口。** 不拆机就能拿到固件的所有通道都被封死，实测确认。
2. **产品上不可接受。** 这是要发给所有用户的软件，不能把「拆机刷固件」写进使用说明。
3. **外部工具包也救不了。** 瓶颈在「取出固件」，不在「分析固件」，而取出的唯一钥匙是拆机。

## 缘起

想验证一件事：能否把按键映射做进设备固件，从源头改键，取代现在「拦下 Windows 已经翻译好的 VK，再 SendInput 注入目标键」的做法。如果可行，钩子、物理键盘误伤、300ms 超时这些工程包袱都能消失。

## 信号链路与可改性

按键从手指到应用经过七层，只有前两层属于「映射层」：

| 层 | 能不能改 | 现实约束 |
|---|---|---|
| 遥控器固件映射 | 够不着 | 无公开 SDK / 刷写口，2.4G 与接收器配对绑定 |
| 接收器固件 | 够不着 | 同上，且查不到该 VID:PID 的任何资料 |
| HID 报文 → Windows 输入栈 | 只是通道 | — |
| Scancode Map（系统映射层） | 覆盖不了 | 只认键盘扫描码；不认消费者页 usage；不能发组合键；全局生效会误伤物理键盘；需重启 |
| RIDEV_NOLEGACY 独占消费者页 | 本机不可用 | 复合设备实测被系统拒绝（err=1004，见 `--own` 注释） |
| 用户态键盘钩子（现状） | 唯一可行 | 拿不到设备来源，会误伤物理键盘；有 300ms 超时限制 |
| 应用收到按键 | 终点 | — |

一个容易被忽略的事实：当前程序其实已经是两条路——Windows 会翻译成 VK 的键（播放/返回/长按返回/灯泡/静音）必须靠钩子拦截；Windows 根本不翻译的键（OK `0x0041`、麦克风 `0x00CF`）走 Raw Input 读原始报文直接注入，**本来就不需要拦截**。所以「从映射层改」的理想，对一部分键早已实现。

## 实测证据

### 1. 软件侧：固件通道被封死

用纯只读探针 scan 了 USB 注册表树、全部 HID 接口、字符串描述符和驱动绑定：

- 设备是复合 USB：`MI_00` 为 USB Audio（Mic Device），`MI_02` 为键盘，`MI_03` 下挂鼠标 / 消费者页 / 系统控制 / 厂商私有页 `0xFF01`。
- 制造商字符串 **`XING WEI 2.4G USB`**，是唯一可搜的方案商线索；网上查不到该 VID:PID 的具体芯片资料。
- 无序列号、固件版本固定 `0x0100`、无 Feature Report、五个接口全部是标准 `HidUsb` 驱动、无 WinUSB / DFU 绑定。
- 结论：**没有固件升级后门，USB 控制传输这条路走不通。**

附带发现：`MI_00` 是 USB Audio，意味着麦克风走 USB 声卡，并非早期文档推测的 ATVV 蓝牙协议。因已放弃深究，此点未继续验证。

### 2. 私有页写入试探：安全，但无果

厂商私有页 `0xFF01` 是唯一看似可写的通道（声明了 17 字节 IN / 9 字节 OUT，其中 OUT 扣掉 Report ID 后 payload 为 8 字节）。针对「会不会刷坏固件」这个担心：

- 用带熔断的探针，每次写入前后都重新枚举并比对五个接口的指纹（page / usage / IN / OUT / FEAT 长度），任一变化立即停止。
- 发全 0（最不可能触发任何命令的值）：`WriteFile` 返回 `err=87`（ERROR_INVALID_PARAMETER）；换 `HidD_SetOutputReport` 重发，同样 `err=87`。
- 两次写入后设备指纹完全一致，遥控器毫发无损。数据根本没进设备。
- 只读尝试读取私有页报告描述符：`MI_03` 下四个集合全部返回 `err=1`（ERROR_INVALID_FUNCTION）；只有键盘接口能读到 28 字节的非标准描述符。

**判断依据**：Output Report 数据只进设备 RAM。要改写 Flash，固件必须主动实现「收到命令 → 进 bootloader → 擦写」的逻辑，而这台设备把 DFU / WinUSB / Feature Report 全关了，存在该逻辑的概率极低；即便存在，盲写 8 字节撞上精确魔数的概率也近乎为零。真正的风险在配置/配对表被改，那可以重新对码恢复，并非永久损坏。实测结果印证了这一点——写入被系统直接拒绝。

### 3. 外部工具包核查

评估了 `reverse-skill`（AI 逆向技能路由包）能否改变结论。它的固件模块明确以「**拿到一份 .bin / .img 文件**」为起点；硬件模块要求拆解设备、用万用表找 GND/VCC/TX/RX、J-Link 枚举 IDCODE。其提取固件的四条路是官网下载、OTA 抓包、UART 落 shell dump、SPI flash 物理读——前两条本机没有固件来源，后两条必须拆机。

它是一套更好的「解剖刀」，但这里没有可解剖的样本；而取出样本的唯一钥匙，正是已被否决的拆机。

## 决定

用户拍板放弃，理由是产品门槛：不能要求每个用户拆硬件。这是经过实测证伪与外部工具核查双重验证的决定，不必再重提。

## 对发布的影响

无。评估全程未改 `bridge.py` 生产代码，未改打包 spec（打包内容仍只有 `bridge.py` + 图标 + `help.html` + `VERSION`）。临时探针脚本与输出记录已全部删除，本文是唯一留存。
