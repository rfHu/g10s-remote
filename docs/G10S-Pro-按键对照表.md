## 一、你关注的 4 个键

| 遥控器图案 | 规范名 | 报文 | 走哪个页 | Windows 翻译成 | 能不能用 AHK 直接抓 |
|---|---|---|---|---|---|
| ▶/⏸ 播放暂停 | Consumer `0x00CD` | `02 cd 00` | 消费者页 | **VK `0xB3`** Media_Play_Pause | 能 |
| ○ 方向中间圆圈（OK） | **两种身份，见下节** | 飞鼠关 `02 41 00` / 飞鼠开 鼠标左键 | 消费者页 或 鼠标页 | 飞鼠关：无任何键；飞鼠开：鼠标左键 | 只有鼠标左键那侧能 |
| ⌂/↩ home/返回 | Consumer `0x0224` AC Back | `02 24 02` | 消费者页 | **VK `0xA6`** Browser_Back | 能 |
| ☰/💡 菜单/灯泡 | 键盘页 `0x5D` AppsKey | Windows 直发键盘事件 | 键盘页 | **VK `0x5D`** AppsKey | 能 |

### OK 键有两种身份，取决于飞鼠开关

实测两组对照，是同一颗键在不同飞鼠状态下的表现：

```
飞鼠关（12:50:47）
  消费者页  ▼按下  usage=0x0041  raw=02 41 00
  消费者页  ▲松开  raw=02 00 00
  → 之后什么都没有

飞鼠开（12:55:14）
  鼠标页    ▼ 鼠标左键按下
  鼠标页    ▲ 鼠标左键松开
  → 只有鼠标左键，没有 0x0041
```

**两种身份是互斥的**：飞鼠开的时候，OK 完全不发 `0x0041`，只发鼠标左键。
所以「OK 键按了没反应」这句话只在飞鼠关时成立。

这对方案是好消息：**只要按设备过滤，OK 键两种情况都能稳定抓到**。

- 收到 `0x0041` → 飞鼠关状态下的 OK
- 收到**遥控器**发出的鼠标左键 → 飞鼠开状态下的 OK
  （这支遥控器上只有 OK 一颗左键，所以 `RC/MI_03` 的左键点击必然是 OK，不会误判）

也就是说：**不需要知道鼠标开关是开还是关**，把两条信号都当成「OK 按下」即可。

### 飞鼠关时它是「死键」：Windows 完全不翻译

`0x0041`（HID 规范的 Menu Pick）**没有被 Windows 的消费者页翻译表收录**。实测证据：

```
[12:50:47.224] RC/MI_03  消费者页  ▼按下  usage=0x0041  raw=02 41 00
[12:50:47.391] RC/MI_03  消费者页  ▲松开  raw=02 00 00
```

同一毫秒**没有任何** `hDevice=0` 的合成键盘事件。对比同时刻的播放/暂停：

```
[12:50:38.373] RC/MI_03  消费者页  ▼按下  usage=0x00CD  raw=02 cd 00
[12:50:38.373] 系统合成          键盘页  ▼按下  播放/暂停  VK=0xB3
```

所以 OK 键按下去，Windows 里等于什么都没发生 —— 这也解释了为什么它「按了没反应」。
任何基于键盘钩子的工具（AutoHotkey 也不例外）都抓不到它，只能靠 Raw Input。

## 三、一个事件都没收到的键

| 遥控器键 | 实测 | 判断 |
|---|---|---|
| 电源 | 0 条事件 | 只发红外（说明书：IR learning key），不进 USB |
| **鼠标开关** | **按了，0 条事件** | **确认是本地功能键**：只切换遥控器内部状态，主机的不到任何通知 |
| 背光 | 未测 | 大概率同为本地功能，不发键值 |

**鼠标开关不报告状态，这件事有一个直接后果**：任何程序都无法知道飞鼠现在是开还是关。
所以方案不能设计成「先判断飞鼠状态再决定怎么处理 OK 键」，只能像上一节说的那样，
把 `0x0041` 和「遥控器发的鼠标左键」两条信号都当作 OK。


厂商私有页 `0xFF01`（17 字节报文）在整个采集过程中 **0 条**。说明按键不走私有通道，
那 17 字节应该是给体感/飞鼠用的。

## 四、映射时「会不会误伤物理键盘」

这是决定方案复杂度的真正因素 —— 不是能不能抓，而是同一键值物理键盘上有没有。

| 键 | 键值 | 物理键盘上有没有这个键 | 重映射的代价 |
|---|---|---|---|
| 返回 | `Browser_Back` 0xA6 | **没有** | 安全，可独占 |
| 播放/暂停 | `0xB3` | 部分键盘有媒体键 | 一般，可能连带 |
| 菜单/灯泡 | `AppsKey` 0x5D | **有**（右键菜单键） | 会抢掉物理键盘的菜单键 |
| 音量 / 静音 | `0xAF` `0xAE` `0xAD` | 部分键盘有 | 一般 |
| OK | 无键值 | — | 不涉及，但必须自建通道 |

`Browser_Back` 那条特别值得利用：物理键盘根本发不出这个键，所以把它改成任意动作
都不会影响你打字。这是四个键里唯一能「干净改造」的。

## 五、对两个需求的影响

### 语音输入（按住麦克风键 → 微信输入法）

麦克风键 = `0x00CF`，**Windows 不翻译**，因此必须有一个常驻的 Raw Input 监听进程，
收到 `0x00CF` 按下/松开时注入 `Ctrl+Win` 的按下/松开。AutoHotkey 的热键在这里无效。

好消息是遥控器发的就是干净的 press / release 两条 （间隔 127ms 起），
「按住说话、松手上屏」的时序天然匹配。

### 按键映射

三个键（播放/暂停、返回、菜单）可以用 AutoHotkey 的普通热键；
**OK 键必须和麦克风键一起走 Raw Input 那条通道**。这也是为什么建议把
「语音触发」和「OK 键映射」放进同一个常驻进程 —— 两者都需要 Raw Input，没必要起两个。

## 六、一个绕不过去的取舍：OK 键改不了「只映射不点击」

飞鼠开着时按 OK，Windows 会把它当成真实鼠标左键点下去。这就带来一个问题：

**想「按 OK 触发某个动作，但不希望它顺手点一下屏幕」是做不到的。** 因为那是一次货真价实的
左键点击，而飞鼠模式下你本来就需要左键去点东西 —— 屏蔽掉它，遥控器就点不了了。

三条路，各有代价：

1. **接受叠加**（推荐）：按 OK 既点击、也触发动作。选动作时避开有破坏性的（如「打开输入法」「切窗口」可以，「关闭窗口」不行）。
2. **只在飞鼠关的状态下用 OK**：那时它是 `0x0041`，Windows 没反应，天然纯信号。需要用户自己知道飞鼠开着还是关着 —— 而遥控器又不告诉你，等于靠人记。
3. **动态判定**：靠「最近一次光标是否在动」猜飞鼠状态，猜错就误触发。不推荐。

## 七、还没确认的

1. **`0x0223`（AC Home）是否存在**。本次没出现，说明书也只写「主页」，
   你这支可能把主页做成红外直发电视，不经过 USB。
2. **背光是否发键值**。按一下看 keywatch 有没有输出即可判定（鼠标开关已确认不发）。

## 八、最终实现（2026-11-17 验收通过）

程序：`bridge.py`，启动脚本 `bridge.bat`。一个进程同时干两件事。

### 播放/暂停 → 回车

- 机制：低级键盘钩子 `WH_KEYBOARD_LL` 拦 `VK 0xB3`，`return 1` 吃掉原键，再 `SendInput` 发回车
- 为什么必须钩子：Raw Input 只能看、不能拦，做不到「不做播放、只发回车」
- 钩子回调里不做注入，只 `PostMessage` 转给消息循环 —— 回调超过 300ms 会被系统**静默摘除**

### 麦克风键 → Ctrl+Win（切换式）

**关键限制：这支遥控器不报告松手。** 三次实测（含按住 7 秒）：

```
13:55:04  02 cf 00   ← 按下
13:55:04  02 00 00   ← 100ms 后归零
（之后 7 秒：消费者页 / 私有页 0xFF01 / 系统控制页 全部静默）
```

设备把「按住」当成「点一下」上报，之后不再说话。两条替代路也都堵死：

| 替代信号 | 实测结果 |
|---|---|
| 私有页 `0xFF01` 心跳 | 按住期间 0 条报文 |
| 音频电平 | 麦克风持续采音（环境声峰值就 500+），没有「按住/松开」的边界 |

所以只能**用两次点击划定起止**：第一次注入 Ctrl+Win 按下，第二次松开。
对微信输入法来说，它看到的仍是一次完整的长按，与真按住键盘无区别。

日志实样（2026-11-17 13:57）：

```
13:57:43  语音输入开始：已注入 Ctrl+Win 按下（再按一次结束）
13:57:51  语音输入结束（再次按下），共持续 7.8 秒
13:58:45  播放键 → 回车（原媒体功能已拦截）
```

### 已知边界

1. 播放键吃掉**所有**键盘的 `VK 0xB3`（钩子拿不到设备来源），物理键盘若有媒体播放键也会变成回车
2. 默认无条件发回车。若在资源管理器里误触（回车会打开选中的文件），可加进程黑名单
3. 微信客户端 4.1.8 自身也绑了 Ctrl+Win，可能双触发；去「微信 > 设置 > 快捷键」改掉客户端那个
4. 捕获 120 秒后自动松开（`VOICE_WATCHDOG_SECS`），防止忘了再按一次导致修饰键一直按住

## 九、消费者页按键总览（全部 7 个）

这支遥控器上走消费者页（Usage Page `0x0C`）的按键，实测只有 7 个。
所有报文都是 **3 字节、Report ID = 0x02**，格式固定为 `02 <usage_lo> <usage_hi>`。

| 遥控器按键 | usage | 报文 | Windows 翻译成 | 当前程序 |
|---|---|---|---|---|
| 播放/暂停 | `0x00CD` | `02 cd 00` | VK `0xB3` | **映射为回车**（原键被拦截） |
| 音量 + | `0x00E9` | `02 e9 00` | VK `0xAF` | 不处理，原样生效 |
| 音量 − | `0x00EA` | `02 ea 00` | VK `0xAE` | 不处理，原样生效 |
| 静音 | `0x00E2` | `02 e2 00` | VK `0xAD` | 不处理，原样生效 |
| 返回 | `0x0224` | `02 24 02` | VK `0xA6` 浏览器后退 | **叠加：后退 + Esc 都发** |
| OK（飞鼠关） | `0x0041` | `02 41 00` | **不翻译，无任何键** | **Alt+Tab 窗口切换** |
| 麦克风 | `0x00CF` | `02 cf 00` | **不翻译，无任何键** | **映射为 Ctrl+Win** |
| （每次松开） | `0x0000` | `02 00 00` | — | 仅用于判定「这次按键结束」 |

两点容易误解的地方：

1. **松开报文不带键值**，统一是 `02 00 00`。所以它只能表示「某次按下结束了」，
   不能表示「哪一个键被松开」——这也是为什么无法靠报文判断按住时长。
2. **OK 键有两种身份**：飞鼠**关**的时候是上面的 `0x0041`；
   飞鼠**开**的时候它变成鼠标左键，完全不发消费者页报文（见第一节）。

### 不走消费者页的按键

以下按键走**键盘页**（`0x01`），有真实的扫描码，和物理键盘无法区分：

| 按键 | VK | 扫描码 |
|---|---|---|
| ↑ ↓ ← → | `0x26` `0x28` `0x25` `0x27` | `0x48` `0x50` `0x4B` `0x4D` |
| DEL | `0x08` | `0x0E` |
| PageUp / PageDown | `0x21` / `0x22` | `0x49` / `0x51` |
| 菜单/灯泡 | `0x5D` AppsKey | `0x5D` | 两个模式都是**回车**（原 AppsKey 被吃掉） |

### 完全不发报文的按键

电源、背光、鼠标开关（纯本地功能，主机收不到任何通知）。

**电源键已实测确认（2026-11-17 19:11）**：监听全部 5 个集合（鼠标 / 键盘 / 消费者页 /
系统控制页 `0x01/0x80` / 厂商私有页 `0xFF01`），连续按多次电源键，**0 条报文**；
期间别的设备（罗技键盘）的记录正常出现，证明监听本身是工作的。
按键后设备仍完整枚举出 5 个接口，说明按电源键不会中断 USB 连接。

结论：电源键只驱动红外 LED（发 `NEC` 码给电视/投影），与 USB HID 是两条独立通路。
软件层面这个键**不存在**，连"被按过"都无法感知，因此不可能映射。

### 补充：返回键 → Esc（2026-11-17 追加）

用途：说话途中反悔，按返回键取消这次语音听写。

- 源键：`VK 0xA6`（返回键被 Windows 翻译成的 Browser_Back）
- 目标键：`VK 0x1B`（Esc）
- 模式：默认 **additive**（后退与 Esc 都发）；`--back replace` 只发 Esc，`--back off` 不接管
- 选 addditive 的理由：打断输出在 WorkBuddy、后退在浏览器，两个场景各自成立，跨场景副作用可接受
- 副作用：浏览器里不再有「后退」，要按 `Alt+←` 或工具栏

实现上把钩子从「只认播放键」重构成一张映射表（`KEY_ACTIONS`）：
`源 VK → (目标 VK, 模式, 日志文案)`，加新键只需加一行。

### 补充：静音键 → 模式切换 / 播放键随模式变化（2026-11-17 追加）

静音键 `0x00E2`（VK `0xAD`）改成模式切换键，两个模式循环：

| 模式 | 上/下键（`VK 0x26/0x28`） | 播放键（`VK 0xB3`） | 返回键（`VK 0xA6`） | 托盘图标 |
|---|---|---|---|
| 对话模式（默认） | 原样方向键 | 拦截并发 Ctrl+N | 拦截并发 Esc | `app-dialog.ico` 绿底气泡 |
| 观看模式 | 拦截并发鼠标滚轮 | **放行，恢复原生媒体控制** | **放行，原生浏览器后退** | `app-watch.ico` 蓝底眼睛 |

要点：

- 滚轮注入必须节流（`WHEEL_MIN_INTERVAL=0.09`），否则方向键自动重复约 30 次/秒
  会让滚屏达到 90 行/秒，完全无法阅读
- 观看模式下播放键与返回键都在钩子里**直接 `CallNextHookEx` 返回**，连日志都不记，等于完全不存在
- 这实际上就是「按前台应用条件化」的替代方案：判断依据是用户手动切的模式，而不是猜前台进程
- 模式不持久化，重启回对话模式

### 补充：菜单/灯泡键 → 鼠标右键（2026-11-17 追加）

- 源键：`VK 0x5D`（Applications 键，扫描码 `0x5D`，走**键盘页**不是消费者页）
- 动作：在**当前光标位置**发一次鼠标右键（`SendInput` + `MOUSEEVENTF_RIGHTDOWN/UP`）
- 模式：replace，原来「在焦点处弹上下文菜单」被吃掉
- 关掉：`bridge.py --menu keep`
- 语义差异（重要）：AppsKey 原本是"在焦点处弹菜单"，改成右键后是"**在光标处**点一下"。
  光标不在目标元素上时，右键会落在光标所在的空白处，不会落到当前焦点上。

### 补充：「第一阶段」被其他按键抢占（2026-11-17 追加）

两个切换式功能存在「第一阶段」状态：语音录音中、Alt+Tab 浮窗打开中。
规则：**按下其他键时，先把第一阶段收尾，再让该键照常生效。**

| 阶段 | 会触发收尾 | 不触发（例外） |
|---|---|---|
| 语音录音中 | 几乎所有键（含方向键、退格、播放键等） | 纯修饰键（Ctrl/Alt/Shift/Win/CapsLock） |
| Alt+Tab 浮窗 | 除例外外的键 | 修饰键 + **左右上下 + Tab**（否则无法选窗口） |

修饰键必须例外，否则我们注入的 `Ctrl+Win`（开语音）会立刻被自己判成「按了别的键」而自我打断。

实现：`preempt_stages(vk)`，在低级钩子的 **按下** 分支最先调用，
直接发修饰键 keyup（微秒级，不触发 300ms 钩子超时），保证「先收尾、后执行」的顺序。

设计取舍：Alt+Tab 浮窗打开时按其他键会**取消切换**（不换窗口），
语音阶段按其他键会结束录音、且该键本身不执行（只用于收尾）。
